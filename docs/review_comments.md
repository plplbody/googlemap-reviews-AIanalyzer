# 仕様書レビュー (Scenarios 1-3)

**担当**: Reviewer (Lead Architect)
**対象**: `docs/仕様書.md`
**目的**: テストケース作成に向けた品質向上およびデザイナー・開発者間の認識齟齬防止

現状の仕様書は「コンセプト」と「ハッピーパス（正常系）」の記述においては優れていますが、実装およびテストを行うための「厳密な定義」としては、以下の点で不足があります。これらは手戻りの原因となるため、修正を求めます。

## 1. 全体共通 (General)

*   [ ] **異常系・エラーハンドリングの欠落**:
    *   各シナリオにおいて、通信エラー、API制限到達時、データ空（0件）時の挙動が定義されていません。
    *   **修正要求**: 各インタラクションフローまたはUI定義に、エラー時の表示（トースト、アラート、Empty State）を明記してください。
*   [ ] **UI状態（States）の定義不足**:
    *   非同期処理（検索、AI分析、学習保存）中の **Loading State**（スケルトンスクリーン、スピナー、ボタンのDisabled状態）の記述がありません。
    *   **修正要求**: U-xx の定義に各状態の挙動を追記してください。

## 2. シナリオ1: 手動検索と評価 (Search & Evaluate)

*   [ ] **「AIスコア最適化」の検証基準が曖昧**:
    *   *記述*: 「リストの並び順とスコアが即座に再計算される」
    *   *課題*: テスターは何をもって「正しく再計算された」と判断すべきか？
    *   **修正要求**: テスト可能な合格基準（Acceptance Criteria）を追記してください。（例：「『雰囲気』重視の場合、Atmosphereスコア4.0以上の店舗が上位3件に含まれること」等）
*   [ ] **検索クエリのバリデーション未定義**:
    *   空文字検索、極端に長い文字列、記号のみの場合の挙動が不明です。
    *   **修正要求**: `searchPlaces` 利用時のクライアント側バリデーションルールを定義してください（例：文字数制限、禁止文字）。

## 3. シナリオ2: いいねとリスト管理 (Like & Interest List)

*   [ ] **「メモ・タグ入力」の制約事項未定義**:
    *   *記述*: 「メモ・タグ入力」
    *   *課題*: メモの最大文字数、使用可能文字、絵文字の扱いは？
    *   **修正要求**: DBスキーマだけでなく、UI上の入力制限（MaxLengthなど）を明記してください。
*   [ ] **「来店済み」解除時の挙動**:
    *   *記述*: トグルをONにするフローのみ記述。
    *   *課題*: 間違えてONにした場合、OFFに戻せるのか？その際、入力したメモや評価データはどうなるのか（保持 or 破棄）？
    *   **修正要求**: トグルOFF時の挙動（データ保持ポリシー）を明確にしてください。

## 4. シナリオ3: 学習とフィードバック (Like & Learn)

*   [ ] **タグ作成の重複・制限ルール**:
    *   *記述*: 「+ AIタグを作成」
    *   *課題*: 既存と同じ名前のタグを作成しようとした場合は？タグの作成数上限は？
    *   **修正要求**: タグ名のユニーク制約有無、およびエラーメッセージを定義してください。
*   [ ] **XP獲得のフィードバック表示時間**:
    *   *記述*: 「アニメーション付きで獲得XP...を表示」
    *   *課題*: 何秒表示するのか？ユーザーが閉じる必要があるのか？（自動消滅 vs 手動Close）
    *   **修正要求**: `U-11 Feedback Popup` の表示時間（Duration）および終了インタラクションを定義してください。

## 5. データ・スキーマ整合性

*   [ ] **Frontend/Backendの型定義連携**:
    *   仕様書の `interface` 定義はTypeScriptですが、Firestoreの実際のデータ構造（Timestamp型など）や、Client側でのDate変換ルールが明記されていません。
    *   **修正要求**: フロントエンドで使用する型定義と、DB保存時の型定義の差異（特に `createdAt`, `updatedAt` の扱い）について、補足資料または注釈を追加してください。

---
**総評**:
現状のドキュメントは「ユーザー体験」の設計図としては機能しますが、「実装・テスト仕様書」としては具体性が不足しています。上記修正を行うことで、QAチームが迷うことなくテストシナリオを作成できるようになります。
